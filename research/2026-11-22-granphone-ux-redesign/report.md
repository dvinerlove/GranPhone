# GranPhone — аудит UX/UI и план редизайна

Дата: 2026-11-22 · Статус: исследование завершено, код не трогали
Доказательная база: `screenshots/` (25+ живых кадров с эмулятора), `code-audit.md` (инвентаризация всего `app/src/main`), `facts.jsonl` (123 проверенных факта из ~40 прочитанных источников).

---

## 1. Резюме

Приложение функционально сильное (разрешения, огромные элементы, минимум шагов — всё правильно для аудитории), но визуально выглядит «собранным из разных эпох». Главная причина — **отсутствие дизайн-системы**: цвета, радиусы и размеры текста разбросаны по коду, экраны нарисованы в разных стилях, а навигация построена на жестах, которые целевой пользователь не обнаружит.

Хорошая новость: в коде уже есть основа токен-системы (`bald_*` атрибуты). Редизайн — это не «переписать всё», а **консолидировать систему + перестроить навигацию и ключевые экраны**.

Три принципа, которые должны лежать в основе нового дизайна (подтверждены исследованием):

1. **Ничего нельзя «угадать»** — всё подписано текстом, всё выглядит как кнопка, нет скрытых жестов. Исследования: только ~60% иконок пожилые интерпретируют верно; 11 из 22 пожилых не поняли иконку «гамбургер»; слабо выраженные «нажимаемые» элементы увеличивают время задачи на 22%.
2. **Ошибку нельзя совершить** — отмена важнее подтверждений, коммит-действия с задержкой/двойным тапом (паттерн iOS Assistive Access), стабильные позиции элементов.
3. **Система не должна «просвечивать»** — главная претензия пользователей к конкурентам (BIG Launcher и др.): системные диалоги, шторка уведомлений, жаргон («haptic feedback»). Это и есть пространство для дифференциации GranPhone: киоск + кастомные поверхности уже есть, надо довести до конца.

### P1 — визуальная непоследовательность («школьный» вид)

- **Случайная палитра.** Ряды дома — зелёный/бирюзовый/серо-голубой/бежевый (`color_1..4` — фиксированные тинты, не несут смысла). Кнопки диалера: розовая удалить / мятная звонок / голубая бэкспейс. Экран звонка: синий «Speaker ON» + красный «Hang up» — и это единственный экран, где палитра хоть что-то значит.
- **Две темы, два мира.** Внутри одного приложения светлый и тёмный варианты ведут себя по-разному (тинты тайтл-бара `color_1` зашиты в 31 лейаут, то есть один и тот же полупрозрачный зелёный поверх любой темы). Тосты всегда светлые (BaldToast.java:79).
- **Иконки разных стилей:** аккуратные векторы (~160 шт.) + растровый клипарт сирены на SOS + системные иконки приложений в списке программ — три визуальных языка.
- **Кнопка «назад» — крестик в сером круге**, без слова. Для аудитории «никогда не держала телефон» слово «Назад» важнее символа.
- **Пустые состояния** — голый текст («Пусто», «Нет будильника…»): рабоче, но безлюдно.

### P2 — качество исполнения

- 123 хардкодных `textSize` (и местами **`dp` вместо `sp`** — tutorial_fragment_1.xml:32,43; alarm_screen.xml:33 — текст не масштабируется настройкой шрифта и ломается на больших размерах).
- 20 хардкодных hex-цветов в лейаутах/драваблах.
- 37 локалей, но `ar` переведён на ~40%, новые строки GranPhone есть только в en/ru/pt-BR — остальные падают в английский.
- Гигантские стрелки прокрутки вверх/вниз — спорная эстетика, но **это правильный паттерн для аудитории** (явное > свайп). Оставить, причесать.

### Что уже хорошо (не ломать)

- Крупные цели нажатия, подписи под иконками, один ряд = одно действие.
- Кастомная верхняя панель статуса крупными иконками — лучше системной.
- Простые списки «одна строка = один элемент» — паттерн Grand Launcher, исследования подтверждают.
- Guard от случайных тапов, отключенные долгие нажатия, киоск-режим, PermissionActivity с объяснениями «зачем нужно разрешение» — прямо в духе iOS Assistive Access.

## 3. Что делают другие (выжимка исследования)

### iOS Assistive Access (Apple) — главный референс по UX-модели
- Отдельный «режим», который **настраивает помощник** (trusted supporter) по мастеру из 8 шагов с отдельным паролем; вся админка — вне режима. У GranPhone уже есть киоск+PIN — не хватает разделения «пользователь / помощник».
- На выбор: сетка (иконки крупно) **или** список (строки крупно) — оба паттерна предлагаются явно.
- Подтверждение ответственных действий двойным тапом; persistent «Назад»; нет шторки, статус-бара, системных диалогов и сторов.
- Телефон+FaceTime слиты в одно «Calls» приложение; вайтлист контактов на вход и выход.

### BIG Launcher / Grand Launcher / Doro — конкуренты
- Общий паттерн: фото-контакты прямо на доме, SOS = красная кнопка → отсчёт → SMS с GPS + звонок на громкой связи (BIG), настройки под паролем.
- Grand Launcher: один пункт на экран — максимально низкая когнитивная нагрузка.
- Doro EVA: меню глаголами («Позвонить», «Посмотреть», «Отправить») — для людей, не знакомых с метафорой «приложение». Сильная идея для GranPhone.
- **Общая слабость всех** = ваше окно: система просвечивает сквозь лаунчер (шторка, пермишены, жаргон). Рецензент бросил конкурента именно из-за этого.
- OEM-режимы (Samsung Easy, Xiaomi Lite, Huawei Simple) — косметические: крупный шрифт, контрастная клавиатура, у Huawei — принудительный максимум громкости. Никакой защиты от ошибок.

### Гайдлайны (WCAG 2.2, WAI-AGE, исследования)
- Мишени: WCAG AA 24px / AAA 44px; Android 48dp ≈ 9мм; для пожилых исследования рекомендуют **≥8мм** (на 30px — 39% ошибок тапа, на 50px+ — ~5%). → цель GranPhone: основные кнопки **64–80dp**.
- Текст: 4.5:1 контраст (лучше 7:1), 12–14pt+ эквивалент, medium/bold, без ALL CAPS, выравнивание влево.
- Иконки: всегда с подписью (точность +33 п.п.), залитые пиктограммы с толстым штрихом, никаких «гамбургеров».
- Красный/зелёный для звонка — конвенцию держать, но дублировать формой и словом (дальтонизм).
- COGA: минимум шагов, никогда не полагаться на память, отмена > подтверждения, стабильные позиции.

## 4. Предлагаемая концепция

### Информационная архитектура (главное изменение флоу)

Сейчас: скрытая страница-2 + свайпы + мёртвые углы. Предлагается модель **«один экран — одна задача, внизу явная навигация»**:

- **Дом = сетка возможностей** (настраиваемая помощником). Все 12 функций доступны, пустых зон нет. Порядок: звонки → контакты → SOS → сообщения → фото → будильники → таблетки → фонарик → программы → настройки.
- **«Настройки» — обычная плитка на доме** (или отдельный «режим помощника» с PIN — см. ниже). Никаких свайпов для навигации.
- **Persistent «Назад»** — нижняя полоса с словом «Назад» (или большая стрелка+слово) на каждом внутреннем экране; X-крестик заменить на явную кнопку «Назад/Закрыть» с текстом.
- **Режим помощника** (как у Apple): PIN → полные настройки, редактор дома, вайтлисты, права. Обычный пользователь видит «Настройки» = громкость, шрифт, яркость — безопасные ручки.

### Дизайн-система (токены — на базе существующих `bald_*`)

- **Цвет:** один базовый светлый фон + **тёмный вариант**; один акцент (зелёный бренда — уже есть в иконке); **семантические роли**: `call_accept` (зелёный), `call_end` (красный), `sos` (красный), `warning` (янтарный). Убрать декоративные тинты рядов `color_1..4` — либо дать им смысл, либо выровнять. Все цветовые пары ≥4.5:1.
- **Типографика:** системный шрифт, 4 уровня (заголовок 28–32sp / основной 21–24sp / вторичный 17sp / мелкий 14sp), везде sp, масштабирование из настроек умножает шкалу ×0.8–1.7 (механизм есть). Никаких dp в textSize, никаких фиксированных 36sp.
- **Компоненты:** один компонент «кнопка» — залитая, с иконкой+словом, радиус 16dp, высота ≥64dp, физический вид (не ghost/outline); один тайтл-бар: заголовок + слово «Назад»; один диалог `BDialog` (есть) довести до стандарта.
- **Иконки:** единый стиль залитых пиктограмм; убрать клипарт сирены; состояние «выключено» — перечёркнутая иконка + подпись, а не только смена цвета.

### Редизайн ключевых экранов

- **Дом:** 2–3 ряда плиток одной высоты, подписи в одну строку (autosize уже есть), SOS — визуально красная плитка всегда на одном месте. Часы — компактная полоса сверху (или виджет), не полэкрана. Индикатор страниц, если остаются, — подписанные стрелки «Ещё».
- **Телефон/диалер:** фото-контакты (BIG Launcher), кнопка «Позвонить» зелёная с словом, «Стереть» нейтральная; убрать розовый/голубой.
- **Звонок:** ввести в семью BaldActivity; «Завершить» красная гигантская + «Громкая связь» переключателем; фото контакта крупно.
- **SOS:** красная кнопка экрана → отсчёт 5с с отменой → SMS+GPS+звонок (паттерн BIG); «Добавить контакт» не должен выглядеть как главное действие.
- **Уведомления/разрешения:** фикс обрезанных кнопок; шаги разрешений нумерованы «Шаг 2 из 5».
- **Контакты:** фото-первый список, имя до 2 строк с ellipsis, никакого переполнения.
- **Пустые состояния:** иконка + одно предложение + одна кнопка («Добавить первый будильник»).

### Проверки качества (что зафиксировать тестами/чеклистом)

- Прогон worst-case данных по каждому экрану (длинные имена — уже ломают контакты и «Разреши ть»).
- Две темы проверяются парно; любой новый цвет — только через токен.
- Текстовый контраст кнопок ≥4.5:1 скриптом.

## 5. Технический путь (важно: Huawei 2017 / EMUI 8 / слабое железо)

- **Остаёмся на Java + Views.** Compose тянет Kotlin-миграцию всего и рискует производительностью на железе 2017 года — не для этого приложения.
- **Токены — на существующих `bald_*` атрибутах** (это уже дизайн-токены); добавить недостающие роли (`bald_sos`, `bald_call_accept` и т.п.) вместо хардкода.
- **Material Components для Android — версия 1.13.0** (последняя с minSdk 21). Даст нормальные кнопки/карточки/диалоги/риппл и Material 3 тему без переписывания. 1.14 требует minSdk 23 — решить по реальной доле API 21/22 устройств. MDC в maintenance mode, но для Views-стека это нормально и поддерживается.
- **Edge-to-edge и новые API игнорировать** — opt-in, на Android 8 безопасно.
- EMUI-специфика: агрессивное убийство фоновых процессов → напоминатели/будильники критично проверять на реальном устройстве; автозапуск/батарея — отдельная инструкция в онбординге помощника.

## 6. Дорожная карта (по приоритету)

1. **P0-хирургия (1–2 дня):** вернуть путь к настройкам на дом (плитка), починить обрезание текста (wrap→ellipsize, dp→sp, обрезанные кнопки «Разрешить/Очистить», часы), сделать SOS достижимым.
2. **Дизайн-токены:** семантические роли цвета, единый радиус/высоты, убрать/осмыслить тинты рядов, CallActivity → в семью темы.
3. **Навигация:** подписанный «Назад», убрать скрытые свайпы, дом = явная сетка, страница 2 → нормальная вкладка/плитка.
4. **Экраны по очереди:** звонок → SOS → диалер/контакты (фото) → уведомления/разрешения → программы → пустые состояния.
5. **Режим помощника** (PIN, вайтлисты, мастер первоначальной настройки) — выравнивание с iOS AA.
6. **Полировка:** анимации ≤300мс нажатий, иконки единого стиля, локализация новых строк, проверка на реальном Huawei.

## 7. Что не проверено / риски

- Скриншоты сняты на эмуляторе 480×800 в светлой теме; тёмная тема и планшет/ландшафт не прогонялись — при реализации нужен тот же тур на обеих темах.
- Экран реального звонка вживую не снят (нет SIM) — оценка по коду и старому скриншоту из docs.
- Поведение на EMUI 8 (убийство процессов, часы/напоминания) — только план проверки, не выполнена.
- Реальная доля устройств на API 21–22 неизвестна — решение minSdk 21 vs 23 отложено.

# Часть II — второй проход: что было пропущено + инструменты, архитектура, рефактор

## 8. Что не смотрел раньше — допроверено (новые находки)

Снято ещё ~15 живых кадров (`screenshots/v3-*`). Новые проблемы:

### P0 (добавки)
- **Заголовки обрезаются повсюду**: «Изменить главный эк…», «Специальные возмо…», «Изменение времени …», «Установить клавиату…», «Добавить таблетку» режет поле «Название Таблет…». Тайтл-бар не умеет ужимать текст.
- **Экран выбора уровня доступности сломан визуально**: кнопки с текстом рвутся посреди слова («Высоки й Урове нь», «Обычн ый уро вень»), строки таблицы «Прокрутк а». **И это же экран №2 онбординга** — первое, что видит новый пользователь.
- **Экран шрифта обрезает собственные подписи размеров** («Малень…», «Бол…») — парадоксальный баг на экране про читаемость.
- **AddAlarm: микромишени.** Чекбоксы дней недели ~20px (нужно ≥56dp для этой аудитории), радиокнопки «Каждый день»/«Только один раз» **перекрывают друг друга** (коллизия текста, кадр v3-13).
- **Клавиатура: нет кириллицы.** Кастомный IME — только английская и иврит раскладки. Для русскоязычной аудитории, которой надо вводить имена контактов — это бьёт по базовому сценарию.
- **Туториал требует свайп** («Проведите влево или вправо», точки-индикаторы) — жест, которого аудитория не знает; альтернативной кнопки «Дальше» нет. Кнопка «Установить домашний экран» в конце сбрасывает дефолтный лаунчер → чейн в системный Resolver. Опечатка «кочестве».

### P1 (добавки)
- **Модалки: 4–6 способов закрытия/выбора в одном окне.** Паттерн BDialog везде: ряд опций (заполненная = выбранная) + `OK`/`Отмена` + крестик `X`. Пример редактора: `SOS | Своё | Скрыть` + `OK | Отмена` + `X` — выбор не применяется мгновенно, «Отмена» vs «X» неразличимы для пользователя.
- **Дропдаун приложений**: фантомная 4-я пустая строка; «+»-иконка у «Добавить Ярлык» (плюс = добавление, а не ярлык), регистр текста непоследовательный.
- **Тосты**: посреди экрана, всегда светлые (`BaldToast.java:79`), машинный перевод («новый будильник названный Таймер создан!»).
- **Строка будильника**: «Измени ть» обрезана; свитч-«Включить/Выключить» текстовый — хорош, оставить паттерн.
- **Контакт-деталь**: имя центрируется и рвётся на 3 строки, нет фото-плейсхолдера крупно (фото-контакты — ключевой паттерн конкурентов).
- **Home top-bar**: колокольчик уведомлений — единственный вход в уведомления, мелкая иконка.
- **KeyboardChanger**: текст обрезан («Трудно использов…») — снова clip-баг.

### Что подтвердилось как хорошее
- AddTimer: чистый экран, большие +/−. SingleContact: «Позвонить» — большая зелёная кнопка с словом. BaldSwitch текстовый. Клавиши кастомной клавиатуры крупные и подписанные. Приложения-дропдаун — рабочий паттерн.
- Кастомный статус-бар на доме с огромными иконками сигнала/батареи/звука — лучше системного, оставить.

## 9. Какие инструменты/стек использовать

**Остаёмся: Java 8 + Views + XML.** Меняем минимум:

| Что | Выбор | Почему |
|---|---|---|
| Билд | **AGP 3.5.3 → 4.2.x, Gradle 5.4.1 → 6.7.x, JDK 11** | минимальный апгрейд, открывает ViewBinding (нужен AGP ≥3.6) и свежие линты. Больший прыжок (AGP 8) требует JDK 17 + namespace + несовместимости — отдельный этап позже, не вместе с редизайном |
| Вью | **ViewBinding** (включается флагом) | типобезопасный доступ к вью; убивает класс багов findViewById; агенту проще править — привязки видны в сигнатуре |
| Дизайн | **`bald_*` токены + Material Components 1.13.0** (последняя на minSdk 21; 1.2.0-beta01 уже в deps — апгрейд, не новая зависимость) | MaterialButton/Card/ripple/надёжные диалоги; Material 3 тему мапим на bald_* атрибуты — не переписывая систему тем |
| DI/архитектура | **ничего нового** | Hilt/Room и т.д. уже есть (Room 2.2.5); DI-фреймворк на 141-файловое приложение — оверкилл; S.java/BPrefs — фактически service locator, оставить, переименовать |
| Тесты | **Espresso + существующий `BaseScreenshotTakerTest`** | харнесс скриншот-регрессии уже в репо — использовать как гейт редизайна (до/после каждого экрана) |
| Иконки | **Material Symbols / Material Icons, вектор XML, filled-стиль** | единый залитый стиль, бесплатно, экспорт в VectorDrawable |
| Шрифт | **системный sans** (Roboto/EMUI-фолбэк) | ноль веса APK, нативно на старом железе |

Не берём: Compose (Kotlin-миграция + риск на железе 2017), Navigation component (переделка всех переходов), новые библиотеки под синглтон-задачи.

## 10. Современная структура и архитектура — без полной переписи

**Что есть:** активити-центричный дизайн эпохи 2019. Базовый `BaldActivity` уже решает сквозные задачи (тема, пермишены, гард, диалоги) — это правильный каркас. Проблемы: бог-классы (SettingsActivity 680 строк, HomeScreenActivity 557, AddContactActivity 514), криптонимы (`S`, `D`, `BDB`, `BDialog`), findViewById, дублированный код в 6 классах кнопок, dead code.

**Целевая структура (инкрементально):**
```
ui/           ← экраны (активити + их лейауты), по фиче: home, calls, contacts, pills…
ui/common/    ← BaldActivity, тайтл-бар, диалоги, базовые вью
design/       ← токены (Themes.java), маппер bald_* → MDC, иконки-конвенции
data/         ← Room, prefs (BPrefs → SettingsRepository)
platform/     ← permisssions, sensors-guard, kiosk, TTS
```
Правила, которые делают структуру «современной» без фреймворков:
- **Один экран = один пакет + ViewBinding + layout**. При касании бог-класса — выносим логику в `XxxController`, активити остаётся тонкой оболочкой. Не трогаем то, что не переделываем.
- **Все строки/цвета/размеры — только через ресурсы/токены.** Линт-правило: запрет литеральных `#`, `textSize="\d` в dp, новых хардкодов.
- **Мёртвый код — удалить, а не перетаскивать** (FeedbackActivity, PhoneActivity-ветка, bald_skin, скрытые ряды page2, TutorialFragment3).
- Криптонимы переименовать разово: `S→AppUtils`, `D→Const`, `BDB→DialogBuilder`, `BDialog→DialogFlags`. Дешёвый рефактор, +50% к читаемости для людей и агентов.

## 11. Лёгкость на старом железе (Huawei 2017, EMUI 8)

- Views+XML вместо Compose: нет runtime-слоя, нет первого-кадра композиции — правильный выбор для API 21+.
- Векторные драваблы (уже так — ~160 шт.), `android:requiresFadingEdge` вместо эффектов, минимум overdraw (цветные подложки не должны рисовать поверх фона без причины).
- Никаких блюров/полупрозрачных стёклышек/теневых стопок — дорого на Mali-830. Физическая «кнопочность» делается цветом+бордером, не 9-слойными тенями.
- Анимации ≤300мс, `Animator` только на transform/alpha; уважать «Remove animations» системы.
- Glide уже есть — оставить для фото; не грузить Bitmap в UI-поток (сейчас в SinglePhotoActivity проверить).
- Аккуратно с `BaldActivity` accidental-guard: proximity-sensor слушается на каждом экране — на старом железе это батарея; кандидат на вынос в базовый сервис/отключение на guard-уровне «Обычный».
- **EMUI-специфика**: автозапуск/батарейная оптимизация убивает AlarmReceiver/ReminderReceiver → в онбординге помощника шаг «открыть системные настройки EMUI» с фотоинструкцией (Huawei → Battery → App launch → GranPhone = Manage manually).

## 12. Как улучшить модалки («куча кнопок»)

Диагноз: BDialog смешивает *выбор опции* и *подтверждение* — два ряда кнопок + крестик, состояние неясно.

**Единый рецепт для всех диалогов:**
- Тип A «выбор из списка»: вертикальный список опций крупными строками с радио-индикатором, применение **мгновенно по тапу**, без OK/Отмена; заголовок + слово «Назад». (COGA: минимум шагов; undo > confirm — выбор обратим, значит подтверждение не нужно.)
- Тип B «опасное действие»: один красный/яркий CTA + одна серая «Отмена», без X; текст кнопки = глагол («Удалить контакт», не «OK»). Для совсем необратимого — паттерн двойного тапа с прогрессом (iOS AA).
- Тип C «информация»: текст + одна большая «Понятно».
- Крестик `X` в углу — убрать везде, заменить текстовой кнопкой внизу (моторно проще, не надо целиться в угол).
- Количество кнопок в модалке: **≤2** плюс сам список опций.

Это один компонент `DialogScreen` (наследник BDialog с тремя конструкторами типов) — не 3 новых виджета.

## 13. Как сделать дизайн «современнее» конкретно

1. **Один визуальный язык:** фон `surface` + белые карточки/кнопки с радиусом 16dp и тонким бордером; акцент один (зелёный бренд) + семантический красный SOS/сброс. Убрать случайные тинты рядов.
2. **Ритм:** сетка 8dp, кнопки высотой 64–80dp, межэлементные 12–16dp — «воздух» вместо заборов.
3. **Типографика:** заголовки medium-weight, лейаут слева (не центрированный текст блоков), никаких капсов кроме SOS.
4. **Иконки:** залитые Material-пиктограммы 28–32dp + подпись всегда; состояние «выкл» — перечёркнуто + подпись.
5. **Состояния:** нажатие = затемнение 8% + лёгкий scale-down (ripple на API 21+ работает через MDC), не только вибрация.
6. **Пустые состояния:** иконка + фраза + CTA.
7. **Фото-контакты:** большие круглые аватары — эмоциональная «современность» + функционально (узнавание лиц проще чтения для аудитории).
8. **Тёмная тема как полноценный второй продукт** (сейчас вторая тема ломает тинты/тосты): фон #121212-подобный, поверхности приподнятые светлее, контрасты пересчитаны по токенам.

## 14. Как сделать код проще для ИИ-агента (и людей)

По убыванию эффекта на труд:

1. **`AGENTS.md` + `DESIGN.md` в корне**: рецепты «как добавить экран/кнопку/токен», запрещённые паттерны (хардкод цветов, dp-в-textSize, новые активити вне BaldActivity), команды сборки/проверки. Это документ, который агент читает первым.
2. **Удалить мёртвое**: FeedbackActivity, PhoneActivity-ветка, bald_skin, help-кнопка INVISIBLE, скрытые ряды page2, TutorialFragment3 — меньше поверхности для ошибок.
3. **ViewBinding** — сигнатурно-явные вью вместо числовых R.id.
4. **Разовые переименования** `S/D/BDB/BDialog` → читаемые имена; `bald.*` в именах новых файлов → `gran*` или нейтральные (пакет можно не трогать — переезд пакета рискован).
5. **Декупликация кнопок**: 6 классов BaldButton* с скопированной логикой вибрации/long-press → один базовый класс/делегат. Агент, правящий один класс, не должен догадываться о 5 близнецах.
6. **Конвенция навигации**: все startActivity — через маленький `Navigation.java` хелпер по фичам (уже полу-есть в S.java) — агент правит один список, а не greps intents по коду.
7. **Скриншот-регрессия** (`BaseScreenshotTakerTest` расширить): агент после правки экрана прогоняет `gradlew connectedDebugAndroidTest -Pscreenshot=…` и сравнивает — самопроверка без человека.
8. **Checkstyle/lint правила** на запрет хардкодов — превращают «не забудь конвенцию» в ошибку сборки.

## 15. Полный рефактор — да или нет?

**Нет, не big-bang.** Приложение работает, у него живые пользователи и хрупкая интеграция (device owner, киоск, InCallService, EMUI). Правильная стратегия — **strangler/incremental**:

- **Волна 0 — фундамент (без визуала):** удалить dead code, переименовать утилиты, поднять AGP→4.2, включить ViewBinding, вынести `DESIGN.md`/токены. Приложение выглядит так же, риск минимальный.
- **Волна 1 — система:** семантические цветовые роли + один `DialogScreen` + один `TitleBar` + один `BigButton` → перекрасить все экраны скопом через токены (это и есть «полная смена дизайна» за малый diff).
- **Волна 2 — флоу:** навигация (явный «Назад», дом-сетка, настройки-плитка), онбординг-помощник, экраны по одному за сессию со скриншот-гейтом.
- **Волна 3 — глубина:** кириллическая раскладка клавиатуры, фото-контакты, SOS-отсчёт, режим помощника.

Полный рефактор «с нуля» отвергаем: риск регрессий на непокрытых путях (звонок, киоск, будильники в :remote процессе) слишком высок; а ценность кода — именно в накопленных костылях под старые Android-версии.

## 17. Звонок вживую (CallActivity через `adb emu gsm call`)

Прогнал входящий, активный и исходящий звонок на эмуляторе (`screenshots/v4-01..10`).

**Находки:**
- **P0 — на экране звонка нет ни номера, ни имени звонящего.** Входящий: заголовок «ВХОДЯЩИЙ ВЫЗОВ» + чёрная пустота на пол-экрана. Активный: «разговор 0:01» + та же пустота. Пользователь не видит, **кто** звонит и **кому** он звонит — базовый контент экрана отсутствует (должны быть фото-аватар + имя огромным кеглем + номер под ним).
- **P0 — системное уведомление перекрывает заголовок** («Идёт разговор / Нажмите, чтобы вернуться к разгов…» поверх текста статуса). Заголовок экрана надо опускать ниже notification-area или не рисовать его вообще.
- **P1 — исходящий на `###` выдал системный MMI-диалог** «Неполадки подключения или неверный код MMI» — системный стиль (тёмно-серый + teal OK), чужероден. Валидировать номер до `ACTION_CALL` (пустой/невалидный → мягкая подсказка в диалере).
- **Хорошо:** «ПРИНЯТЬ»/«ОТКЛОНИТЬ» и «Громкая связь вкл.»/«ЗАВЕРШИТЬ» — эталонные кнопки (полноширинные, цвет+иконка+слово). «ЗАВЕРШИТЬ» вместо «ПОВЕСИТЬ» уже приятно.
- **Наблюдение:** строка-подсказка диалера «1 → 101» (круг с цифрой + номер) нечитаема по смыслу — это подсказка T9/быстрого набора; нужен формат «Имя — номер» или убрать.

## 18. Краш при пересоздании (P0, реальный баг)

При пересоздании HomeScreenActivity (rotation/force-restart) падает:

```
NPE: ImageView.setImageLevel(int) on null
HomeScreenActivity$2.onSignalStrengthsChanged (HomeScreenActivity.java:150)
```

`PhoneStateListener signalListener` стреляет до присвоения `signalView` или после смерти view — нет null-guard/unregister. **Последствие хуже краша**: система выполняет `Clearing package preferred activities` — лаунчер теряет статус «домашнего по умолчанию» и юзер попадает в системный выбор. На живом устройстве любой краш home = потеря дефолта. Фикс тривиальный: null-check + отписка listener'а в onDestroy.

**Смежный баг:** `FakeLauncherActivity` (трюк для вызова chooser'а) показывается в выборе лаунчера второй строкой с тем же именем «GranPhone» — юзер видит два идентичных пункта; если выбрать фейковый «ВСЕГДА», он тут же отключается → дом «ломается» до следующего выбора. Дать Fake другой label («GranPhone — настройка») или отфильтровать.

## 21. Как правильно строить настройки для этой аудитории

Из ресёрча (BIG Launcher PIN-защита, Assistive Access trusted supporter, COGA) + живого аудита:

**Главный принцип — два слоя:**
- **Настройки пользователя** (5–8 пунктов): громкость, яркость, размер шрифта, тип нажатия, фонарик-автомат, вибрация. Открыты, без опасных опций.
- **Настройки помощника** (всё остальное): PIN/долгое удержание+подтверждение. Контакты-вайтлист, плитки, приложения, разрешения, киоск, клавиатура, сброс. У нас уже есть device-owner — PIN-гейт реализуем поверх.

**Правила экрана настроек:**
- Плоский список ≤2 уровней глубиной; строка = иконка + название + **текущее значение** + chevron («Размер шрифта — Обычный»).
- Тоглы применяются мгновенно (свитч), без диалогов OK/Отмена.
- Группы-заголовки: «Звонки», «Экран и звук», «Кнопки и нажатия», «Для помощника» (внизу, за PIN).
- Опасные опции (сброс, разрешения, device owner) — в самый низ, отдельной секцией «Осторожно» с красным маркером.
- Превью там, где можно: выбор шрифта показывает строку-пример на том же экране (у FontChangerActivity уже задумано — образец надо сделать большим).
- Любая системная настройка (яркость, громкость) — слайдер прямо в строке, не переход.

## 22. Постраничные спеки — как сверстать «максимально современно»

Общие токены (расширение `bald_*`): `surface` #F2F4F7 / dark #101418; `card` #FFF / dark #1C2126, radius 16dp, border 1dp #E2E5E9; акцент `brand` #2E7D32; `danger` #D32F2F; `info` #1565C0. Текст: `textPrimary` #14171A (4.5:1+ на любом фоне), `textSecondary` #4A5560. Кнопки: высота 72dp, иконка 28dp + лейбл 20sp medium, radius 16dp, pressed = 8% затемнение. Тайтл-бар 64dp: название 24sp слева + кнопка «Назад» (текст, не иконка) слева/справа.

| Экран | Текущее | Спека |
|---|---|---|
| **Дом** | часы-карта + 4 ряда по 3 цветных тайла | Часы+дата одной карточкой (убрать clip), статус-бар миниатюрный сверху. Тайлы: единый цвет `card`, иконка 32dp чёрная + лейбл 18sp; цвет только у SOS (красная карта) и Телефон (зелёная). # Часть IV — чеклист перед реализацией (что проверить до первого коммита)

Из внешних источников (Android Developers, Play Console Help, dontkillmyapp, NN/g, Feathers, accessibility-гайды) + наши находки. Группировка по риску.

## 24. Сохранение поведения (перед любым рефактором)

- [ ] **Golden-master скриншоты всех экранов до старта** — уже частично есть (`screenshots/` v1–v4); доснять оставшиеся (уведомления, контакт-поиск, pill-деталь, alarm-экран при реальном срабатывании, dark-версии всех экранов). Это наш characterization-базис: после рефактора экран должен выглядеть не хуже и вести себя так же (Feathers: тест фиксирует *текущее* поведение, включая странности).
- [ ] **Инвентарь BPrefs-ключей** — выгрузить все ключи из `BPrefs.java` (десятки `CUSTOM_*_KEY`, темы, гард, нажатия). Рефактор НЕ должен менять имена/дефолты — иначе у существующих юзеров слетят настройки. Одна строка-таблица ключей → контракт.
- [ ] **Room schema export** (`exportSchema=true` + `room.schemaLocation`) — сейчас схема не экспортируется → любое изменение БД слепое. Включить до первого изменения entities.
- [ ] **Тест пути обновления**: поставить ТЕКУЩИЙ релизный APK, засеять данные (контакты, плитки, будильники, таблетки) → обновить новой сборкой → проверить, что всё на месте. Чистый инсталл такого не ловит.
- [ ] **Дубли в выборе лаунчера**: `FakeLauncherActivity` — решить судьбу (другой label / фильтрация) до релиза.
- [ ] **Список «не ломать»**: `InCallService` (нельзя вернуть null-биндинг — Telecom отвалится на стоковый диалер!), `BOOT_COMPLETED`→AlarmReceiver, SOS-цепочка end-to-end, device-owner provisioning, `:remote` процессы, `RoleManager`-фолбэки.

## 25. Платформенные договоры и политики

- [ ] **ROLE_DIALER требования** (developer.android.com): `ACTION_DIAL` UI + полный `InCallService` (incoming + ongoing UI). Уже есть — но волна рефактора не должна регистрировать/дeregister компоненты роль-ритуала.
- [ ] **Play Store политика SMS/Call Log**: `READ_CALL_LOG`/`SEND_SMS` разрешены только активному дефолтному Phone-handler; требуется Permissions Declaration Form + privacy policy + core-functionality в описании. Если канал — только F-Droid, не блокер; **решить до релиза, идём ли в Play** (тогда ещё и targetSdk 29 → обязателен апгрейд targetSdk, Play сейчас требует ~34+).
- [ ] **`applicationId` уже сменён** (`com.granphone.launcher`) — старые пользователи BaldPhone теряют данные при миграции; решено сознательно, но в FAQ/онбординге отразить.
- [ ] **Kiosk/device-owner**: `fullApp`, `recentCalls` — manifest placeholders от flavor'ов; собрать ВСЕ flavor'ы до старта (не только debug) — плейсхолдеры и enabled-флаги компонентов отличаются.

## 26. Доступность — прогон до редизайна (базис «до»)

- [ ] **TalkBack-проход** по 5 ключевым путям (дом → звонок, входящий → ответ, SOS, контакт, настройка): слышно ли имя/роль/состояние элементов, все ли действия доступны свайпом.
- [ ] **`AccessibilityChecks.enable()` в Espresso** — одна строка в test-runner'е, гоняет ATF (тот же движок, что Accessibility Scanner) на каждом view-action. Подключить ДО рефактора → получим автоматический регресс-гейт.
- [ ] **font_scale системы** — подтверждено, что игнорируется (dp-текст); после фикса на sp прогнать 0.85/1.0/1.3/максимум и проверить отсутствие clip'ов.
- [ ] **Display size (крупный экран)** отдельно от font — другое системное колесо.
- [ ] **Контраст-аудит текущих цветов** — зафиксировать «до» (зелёные/бирюзовые/серые ряды — посчитать реальные цифры, не глазомер).
- [ ] **Жестовые альтернативы**: инвентарь всех swipe/long-press-действий → у каждого должна быть кнопочная альтернатива (Android: custom actions для gesture-based).

## 27. OEM-батарея: Huawei/Xiaomi (dontkillmyapp)

Целевая платформа Huawei 2017/EMUI 8 — **агрессивное убийство фона = будильники и таблетки молчат**. Чеклист до реализации:
- [ ] Проверить текущее поведение: ставит ли `AlarmReceiver` `setExactAndAllowWhileIdle` (не `setExact` — Doze откладывает), перерегистрирует ли алярмы после `BOOT_COMPLETED` и `force-stop`.
- [ ] Инвентарь нужных OEM-настроек для EMUI 8: Battery → App launch → Manage manually (3 тогла: auto-launch, secondary, run in background); «защищённые приложения». Записать точные пути меню — в онбординг помощника пойдут фотоинструкции.
- [ ] Xiaomi/MIUI: Autostart permission + Battery saver «No restrictions» + lock in recents — если планируем поддерживать.
- [ ] Решить: показывать ли пользователю/помощнику встроенную проверку «напоминания могут не сработать» (как делают Life Reminders/everbud — 90% саппорт-запросов именно это).
- [ ] `WAKE_LOCK`/`USE_FULL_SCREEN_INTENT` для экрана будильника — проверить манифест.
